# LTO audit: сверка YoYotta PDF с Linux СХД

Скрипт `lto_audit.py` сравнивает один или несколько PDF-манифестов YoYotta с файлами под одним или несколькими корнями Linux.

Он работает только с метаданными:

- полный относительный путь;
- имя файла;
- логический размер файла в байтах;
- имя кассеты из `/Volumes/<TAPE>/...`.

Хеши не вычисляются. Исходные деревья не изменяются.

## Правила сравнения

1. Из пути YoYotta удаляется `/Volumes/<имя_кассеты>/`.
2. На Linux путь берётся относительно каждого `--root`.
3. Верхняя папка проекта (`07-11-2024`, `досъём`, и т. п.) остаётся частью ключа.
4. Регистр игнорируется.
5. Unicode приводится к NFC и сравнивается через `casefold()`.
6. Единицы размера YoYotta задаются при извлечении через
   `--pdf-size-units decimal|binary`. Для новых извлечений по умолчанию
   используется `decimal`: KB = 1000 байт, MB = 1000², GB = 1000³, TB = 1000⁴.
7. Режим `binary` сохраняет прежнее толкование: KB = 1024 байта, MB = 1024² и
   т. д. Выбранный режим сохраняется в SQLite как `pdf_size_units`.
8. Значение из PDF считается округлённым. Например, для `23.29 GB` вычисляется допустимый диапазон точных размеров, которые могли округлиться до этого значения.
9. Скрытые файлы и каталоги пропускаются.
10. Символические ссылки не обходятся и не включаются.
11. Файлы нулевого размера считаются ошибочными и не попадают в автоматический список копирования.
12. Возможный перенос файла ищется только внутри той же верхней папки: совпадают имя без учёта регистра и размер, но отличается промежуточный путь.
13. Имена Linux, содержащие байты вне UTF-8, не приводят к остановке сканирования. Точные байты пути сохраняются в SQLite, а в CSV показываются как `\xNN`. Такие записи получают статус `INVALID_FILESYSTEM_ENCODING` и не включаются в автоматические списки копирования.

## Особенность image sequences YoYotta

YoYotta иногда сворачивает последовательность в одну запись вида:

```text
First : A001.png
Last  : A003.png
Frames: 3
```

Скрипт разворачивает такие PNG/EXR/DPX и другие числовые последовательности в
отдельные пути. Размер первого и последнего файла известен из PDF. Размер
промежуточного файла в PDF отсутствует, поэтому он получает статус
`MATCH_PATH_ONLY_SIZE_UNKNOWN` при совпадении пути и отдельно попадает в
`ambiguous.csv`/`parse_issues.csv`.

На очень длинных строках текстовый слой PDF может перенести окончание `Path` на
следующую строку. Parser восстанавливает его только когда первая часть явно
заканчивается `/`, а следующая строка не является другим полем YoYotta. Редкое
наложение длинного filename на правую колонку `Size` также восстанавливается и
сохраняется как диагностический `entry_line_layout_recovered`. Если сокращённое
поле `Name` содержит `...`, но полный filename в `Path` отличается, исходный
`name_path_disagreement` намеренно остаётся видимым; для file identity
авторитетен полный `Path`.

## Установка в venv

```bash
python3 -m venv ~/venvs/lto-audit
source ~/venvs/lto-audit/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-lto-audit.txt
```

## Центральная inventory database

Новый основной workflow отделяет одноразовый локальный scan RAID от последующей
работы с LTO-манифестами. Central process не обходит RAID по SMB/NFS: каждый
snapshot создаётся непосредственно на storage-server и затем переносится на
центральную машину.

### 1. Создать или мигрировать central DB

```bash
python lto_audit.py init-db --db ~/lto-inventory/lto_inventory.sqlite3
```

Схема имеет явную версию `PRAGMA user_version=3`. Миграция эволюционная:
существующие `lto_entries`, `storage_entries`, metadata и audit reports не
удаляются. Добавляются:

- `servers`, `volumes`, `storage_scans`, `storage_files`;
- `storage_scan_issues`;
- `archive_imports`, `archive_catalog_files`, `archive_manual_map`.
- `lto_reports`; поля связи `report_id` в `lto_entries`, `parse_issues` и
  `report_stats`.

Явная миграция v2 → v3 создаёт по одному legacy report для каждого уже
сохранённого `source_pdf` и привязывает к нему старые entries, parse issues и
stats. Исходные PDF при миграции не перечитываются, поэтому у legacy reports
`content_sha256` остаётся `NULL`. Все storage inventory и XLSX-таблицы остаются
без изменений.

`storage_files` идентифицирует физическую запись через scan/server/volume и raw
relative path. Поэтому одинаковый путь на двух серверах остаётся двумя файлами.
Индексы добавлены только для будущих реальных lookup patterns: volume+path,
filename+size и cassette hints.

### 2. Один раз просканировать локальные volumes

Команды выполняются на соответствующих storage-server, по локальным mount
points:

```bash
# videoserver00 / 192.168.137.89
python lto_audit.py scan-storage \
  --server videoserver00 --server-ip 192.168.137.89 \
  --volume VIDEO10 --root /mnt/VIDEO10 \
  --output VIDEO10_inventory.sqlite3

# videoserver02 / 192.168.137.90: повторить для VIDEO3 и VIDEO5
# videoserver05 / 192.168.137.96: повторить для VIDEO4, VIDEO6 и VIDEO7
```

`scan-storage` обходит всё дерево volume, а не только `SOURCE`, используя
`os.scandir` и `stat`. Содержимое файлов не читается, хеши не вычисляются,
symlink не обходятся. Exact logical size, `mtime_ns`, normalized path и raw path
bytes сохраняются в автономном SQLite snapshot. Source mount должен быть RO;
SMB/CIFS/NFS/SSHFS отклоняются, потому что snapshot обязан строиться локально.
Существующий `--allow-rw-source` разрешает только осознанное тестирование на
writable local filesystem и не разрешает remote filesystem.

Готовый snapshot имеет собственный `snapshot_id` и schema version 1. Уже
существующий `--output` не перезаписывается.

### 3. Импортировать snapshots

После копирования snapshot-файлов на центральную машину:

```bash
python lto_audit.py import-storage-scan \
  --snapshot VIDEO10_inventory.sqlite3 VIDEO3_inventory.sqlite3 \
             VIDEO5_inventory.sqlite3 VIDEO4_inventory.sqlite3 \
             VIDEO6_inventory.sqlite3 VIDEO7_inventory.sqlite3 \
  --db ~/lto-inventory/lto_inventory.sqlite3
```

Каждый snapshot импортируется транзакционно. Повтор того же `snapshot_id` с той
же identity возвращает `ALREADY_IMPORTED` и не создаёт дубликаты. Тот же ID с
другим server/IP/volume/root или другими итоговыми counters считается
конфликтом. При идемпотентном повторе также построчно сверяются metadata файлов
и scan issues, поэтому подмена содержимого snapshot при сохранённом ID не
принимается молча.

### 4. Один раз импортировать исторические XLSX

```bash
python lto_audit.py import-archive-catalog \
  --file "MC2 - LTO Backups.xlsx" \
  --db ~/lto-inventory/lto_inventory.sqlite3

python lto_audit.py import-manual-catalog \
  --file LTO_BACKUPS_MC.xlsx \
  --db ~/lto-inventory/lto_inventory.sqlite3
```

Первый importer потоково читает фактическую четырёхколоночную пофайловую
структуру и сохраняет project/cassette/path/filename вместе с workbook, sheet и
row. Второй читает column-oriented ручную карту: sheet является project hint,
row 1 содержит cassette, optional row 2 — tape/project note, остальные cells —
исходный folder/path text. Служебный и ошибочный текст не отбрасывается.

Обе книги читаются напрямую как OOXML стандартной библиотекой; worksheets не
загружаются целиком. Повтор неизменённого файла идемпотентен. Изменение уже
импортированного workbook на том же пути считается конфликтом.

Cassette labels нормализуются отдельным консервативным правилом: однозначный
generation suffix (`FF7480L7` → `ff7480`, `CTH342L7` → `cth342`) удаляется, но
исходная строка сохраняется. Неизвестные форматы не угадываются.

Проверка реальных файлов дала 403858 строк `archive_catalog_files` и 458 строк
`archive_manual_map`.

### 5. Добавлять новые YoYotta PDF

```bash
python lto_audit.py import-pdf \
  2026-09-01_1833_MESTO_SILY.pdf \
  --db ~/lto-inventory/lto_inventory.sqlite3
```

Можно передать несколько PDF одним вызовом; каждый из них импортируется своей
атомарной транзакцией. По умолчанию размеры PDF интерпретируются как decimal.
Для отчёта с двоичными единицами используйте `--pdf-size-units binary`.
Смешивание разных интерпретаций в одной базе отклоняется, чтобы не смешивать
несопоставимые интервалы размеров.

`import-pdf` использует тот же `parse_yoyotta_pdf()`, что и прежняя команда
`extract`. Поэтому сохраняются tape extraction, Unicode normalization,
decimal/binary rounded size intervals, First/Last expansion, unknown individual
sizes, повторные manifest records и parse issues. Старые reports и entries не
очищаются.

Идентичность PDF — SHA-256 его содержимого. Хеш вычисляется только для самого
PDF-отчёта, никогда не для media files. Копия уже импортированного PDF под другим
путём или именем возвращает `ALREADY_IMPORTED` и не запускает дорогой parser
повторно. Одинаковое имя файла с другим содержимым имеет другой SHA-256 и
создаёт новый report. Файл хешируется повторно после parsing; если он изменился
во время обработки, импорт отклоняется.

Для каждого report сохраняются numeric `report_id`, content SHA-256, первый
увиденный source path/filename, размер и mtime PDF, UTC-время импорта,
`project_header` и режим единиц. Header `Project` — metadata всего YoYotta
report, а не достоверная project identity каждой строки mixed-project PDF.
Legacy-колонка `lto_entries.project` остаётся денормализованным parser provenance
для совместимости и не должна использоваться matcher'ом как authoritative hint.

Следующий этап central workflow — database-only matcher. Он намеренно не входит
в Phase 6: `import-pdf` не сканирует RAID, не строит folder mapping и не запускает
новый audit against inventory.

## Рекомендуемое RO bind-монтирование

Пример для двух массивов:

```bash
sudo mkdir -p /mnt/AUDIT_RO/VIDEO6_SOURCE
sudo mkdir -p /mnt/AUDIT_RO/VIDEO7_SOURCE

sudo mount --bind /mnt/VIDEO6/KANSK/SOURCE /mnt/AUDIT_RO/VIDEO6_SOURCE
sudo mount -o remount,bind,ro /mnt/AUDIT_RO/VIDEO6_SOURCE

sudo mount --bind /mnt/VIDEO7/KANSK/SOURCE /mnt/AUDIT_RO/VIDEO7_SOURCE
sudo mount -o remount,bind,ro /mnt/AUDIT_RO/VIDEO7_SOURCE

findmnt -T /mnt/AUDIT_RO/VIDEO6_SOURCE
findmnt -T /mnt/AUDIT_RO/VIDEO7_SOURCE
```

В `OPTIONS` должно присутствовать `ro`.

По умолчанию скрипт проверяет это через `findmnt` и отказывается сканировать writable-монтирование. Параметр `--allow-rw-source` существует только для осознанного тестирования.

## Один полный запуск

```bash
source ~/venvs/lto-audit/bin/activate

python /path/to/lto_audit.py all \
  --pdf /path/to/KANSK_report.pdf \
  --pdf-size-units decimal \
  --root /mnt/AUDIT_RO/VIDEO6_SOURCE /mnt/AUDIT_RO/VIDEO7_SOURCE \
  --out-dir ~/lto-audit/KANSK_2026-07-22
```

Несколько PDF можно передать после одного `--pdf`:

```bash
--pdf report_part1.pdf report_part2.pdf report_tape_CTH355.pdf
```

Каталог вывода не должен находиться внутри ни одного `--root`.

## Раздельный запуск

Полезно, если требуется повторить только сравнение.

### 1. Извлечь PDF

```bash
python lto_audit.py extract \
  --pdf KANSK_report.pdf \
  --pdf-size-units decimal \
  --db ~/lto-audit/KANSK/audit.sqlite3
```

`decimal` является значением по умолчанию для новых извлечений. Если конкретный
PDF действительно использует двоичные единицы, укажите
`--pdf-size-units binary`. Интервалы в `lto_entries` сохраняются уже в байтах,
поэтому смена режима после извлечения не переинтерпретирует существующие строки.
Чтобы исправить режим, необходимо заново выполнить `extract` без `--append` для
всего комплекта PDF, а затем повторить `compare` и `deletable-folders`.

При `--append` режим нового PDF должен совпадать с режимом существующих записей.
Смешивание decimal- и binary-интервалов в одной базе отклоняется. Базы старых
версий без `pdf_size_units` распознаются как `LEGACY_BINARY_ASSUMED`; read-only
отчёт выводит предупреждение, но не изменяет базу.

Для добавления ещё одного отчёта без очистки уже загруженных:

```bash
python lto_audit.py extract \
  --append \
  --pdf KANSK_second_report.pdf \
  --db ~/lto-audit/KANSK/audit.sqlite3
```

### 2. Найти проекты и сопоставить папки LTO

Если один PDF содержит верхние папки из разных проектов, после `extract` можно
выполнить read-only discovery по корням RAID:

```bash
python lto_audit.py discover \
  --db ~/lto-audit/MIXED/audit.sqlite3 \
  --raid-root /mnt/VIDEO6_RO \
  --raid-root /mnt/VIDEO7_RO \
  --raid-root /mnt/VIDEO8_RO \
  --out-dir ~/lto-audit/MIXED/discovery
```

Команда не разбирает PDF повторно и не меняет SQLite. Она открывает готовую базу
через `mode=ro&immutable=1`, ищет каталоги `<RAID>/<project>/SOURCE` и проверяет
верхние физические папки несколькими точными относительными путями из
`lto_entries`. Для известных размеров также используется сохранённый интервал
округления YoYotta. Имена сравниваются без учёта регистра с NFC-нормализацией.
Формат даты не предполагается, поэтому `DI`, `PROXY`, `20240905_3` и другие
произвольные имена обрабатываются одинаково.

По умолчанию `SOURCE` ищется не глубже двух компонентов от RAID-корня. Предел
можно изменить через `--max-source-depth`. Для папки выбирается до пяти anchors
(`--anchors-per-folder`), распределённых по разным подкаталогам; статус
`MATCHED` требует минимум два известных path+size совпадения
(`--min-anchor-matches`). Одинаковый LTO-путь на нескольких кассетах считается
одним доказательством. Записи последовательностей с неизвестным индивидуальным
размером могут подтвердить существование пути, но сами по себе никогда не дают
`MATCHED`.

Сначала проверяются только одноимённые папки непосредственно под найденными
`SOURCE`. Если их нет, выполняется дешёвый fallback: для верхних папок проверяются
выбранные точные подпути. Полный рекурсивный scan всех RAID при discovery не
выполняется, содержимое медиафайлов не читается, хеши не вычисляются, symlink не
используются. Fallback использует только подпути, отличающие данную верхнюю
LTO-папку от других папок того же манифеста.

Результаты:

- `MATCHED` — ровно один кандидат подтверждён несколькими точными anchors и
  известными размерами;
- `AMBIGUOUS` — правдоподобных кандидатов несколько;
- `NAME_MATCH_UNVERIFIED` — кандидат найден, но известных доказательств
  недостаточно;
- `NOT_FOUND` — ни одно безопасное соответствие не найдено.

Создаются `discovery_mapping.csv`, `discovery_ambiguous.csv` (неоднозначные и
непроверенные строки) и `discovery_not_found.csv`. Основной CSV содержит LTO-имя и его нормализованный
ключ, RAID, проект, каталог `SOURCE`, физическую папку, число кандидатов,
счётчики path/size anchors и детерминированную причину уверенности. Каталог
`--out-dir` обязан находиться вне всех переданных RAID-корней. RAID-монтирования
проверяются существующим механизмом `findmnt` и должны иметь `ro`.

Пример терминала:

```text
LTO folder  Project     Physical folder                                  Status
----------  ----------  -----------------------------------------------  ---------
20240711    MESTO_SILY  /mnt/VIDEO6_RO/MESTO_SILY/SOURCE/20240711        MATCHED
DI          PROJECT_X   /mnt/VIDEO7_RO/PROJECT_X/SOURCE/DI                MATCHED
20240905    ?           -                                                AMBIGUOUS
OTHER       ?           -                                                NOT_FOUND

MATCHED: 2
AMBIGUOUS: 1
NOT_FOUND: 1
UNVERIFIED: 0
```

### 3. Просканировать массивы

```bash
python lto_audit.py scan \
  --root /mnt/AUDIT_RO/VIDEO6_SOURCE /mnt/AUDIT_RO/VIDEO7_SOURCE \
  --db ~/lto-audit/KANSK/audit.sqlite3
```

Старый `scan --root ...` полностью сохранён. Чтобы сканировать только безопасно
сопоставленные discovery-папки, вместо `--root` передайте основной mapping:

```bash
python lto_audit.py scan \
  --mapping ~/lto-audit/MIXED/discovery/discovery_mapping.csv \
  --db ~/lto-audit/MIXED/audit.sqlite3
```

Scanner принимает исключительно строки `MATCHED`; `AMBIGUOUS`, `NOT_FOUND` и
`NAME_MATCH_UNVERIFIED` пропускаются. Каждая физическая папка сканируется
отдельно, но в `norm_path` подставляется её LTO top-folder identity, поэтому
существующая строгая логика сравнения остаётся без изменений. `source_root`
сохраняет настоящий каталог проекта `SOURCE`, `absolute_path` — настоящий путь
файла, а raw bytes относительного пути — физическое имя папки. Это сохраняет
различие проектов и корректный физический путь даже при fallback с другим
именем папки.

### 4. Выполнить сравнение

```bash
python lto_audit.py compare \
  --db ~/lto-audit/KANSK/audit.sqlite3 \
  --out-dir ~/lto-audit/KANSK/reports
```

### 5. Найти полностью представленные на LTO верхние папки

```bash
python lto_audit.py deletable-folders \
  --db ~/lto-audit/KANSK/audit.sqlite3 \
  --out-dir ~/lto-audit/KANSK/deletable-report \
  --simple-size-tolerance-percent 0.1 \
  --simple-size-tolerance-bytes 10485760
```

Команда строит отчёт по уже готовому `audit.sqlite3`. Повторное сканирование СХД
и повторный разбор PDF не выполняются. В базе должны присутствовать как строки
`storage_entries`, так и строки `lto_entries`, то есть до этого должны успешно
завершиться команды `extract` и `scan` (либо `all`). Запуск `compare` для создания
папочного отчёта не обязателен: классификация файлов вычисляется заново напрямую
из двух манифестов в SQLite.

База открывается через SQLite URI `mode=ro` как неизменяемый снимок. Команда не
инициализирует и не мигрирует схему, не обновляет `metadata`, не создаёт checkpoint
и не должна создавать рядом с базой файлы `-wal` или `-shm`. Если такие служебные
файлы уже существуют, запуск останавливается: это может означать активную запись
или незавершённый WAL-снимок. Не удаляйте эти файлы вручную; сначала корректно
завершите процесс, который пишет базу, и используйте согласованный закрытый
снимок `audit.sqlite3`.

Каталог `--out-dir` создаётся только после проверки безопасности. Он не может
находиться внутри ни одного корня СХД, сохранённого в базе. Все записи команды
ограничены явно указанным каталогом отчёта.

#### Идентичность физической папки

Одна строка папочного отчёта соответствует паре:

1. `source_root` — конкретный корень СХД;
2. точные исходные байты первого компонента относительного пути под этим корнем.

Поэтому одно и то же отображаемое имя верхней папки на двух массивах создаёт две
независимые строки. Формат имени не анализируется: папка может называться датой,
произвольным текстом, содержать пробелы или Unicode. Для физической идентичности
не используется только нормализованная текстовая форма.

#### Как принимается решение

Для каждого отсканированного обычного файла заново вычисляется индивидуальная
классификация. Папка получает `SAFE_TO_DELETE`, только если каждый её файл имеет
подтверждённое совпадение полного нормализованного относительного пути и точный
размер Linux входит в известный интервал округления YoYotta.

Папка получает `BLOCKED`, если обнаружено хотя бы одно из условий:

- файл отсутствует в LTO-манифесте;
- полный путь совпал, но размер не входит в интервал YoYotta;
- файл на СХД имеет нулевой размер;
- размер LTO неизвестен;
- найден только возможный перенос или неоднозначный кандидат;
- путь СХД содержит байты вне UTF-8;
- известные интервалы повторных LTO-записей конфликтуют;
- одинаковый нормализованный путь найден на СХД с разными размерами;
- не все отсканированные файлы получили завершённую классификацию;
- есть `directory_read_error`, `file_stat_error` или другая ошибка сканирования,
  из-за которой состав папки мог быть определён не полностью.

Одинаковые интервалы одного пути на нескольких LTO-кассетах не блокируют папку.
Одинаковые файлы под разными корнями СХД классифицируются отдельно; копии с
разными размерами считаются проблемным дубликатом.

Название `SAFE_TO_DELETE` означает только результат аудита. Скрипт не удаляет,
не перемещает и не переименовывает файлы и не создаёт команды `rm`.

#### Выходные файлы

Создаются только информационные отчёты:

- `deletable_folders.csv` — только папки с решением `SAFE_TO_DELETE`;
- `blocked_folders.csv` — только заблокированные папки с причинами;
- `folder_size_comparison.csv` — все физические верхние папки, удобно для
  визуального сравнения размеров независимо от решения;
- `simple_folder_check.csv` — компактная операторская сверка полного размера и
  числа файлов папки СХД с полной папкой LTO;
- `deletable_folders.txt` — отображаемые абсолютные пути безопасных папок, по
  одному на строку;
- `deletable_folders.nul` — точные байты тех же абсолютных путей с NUL-разделителем.

CSV-файлы сортируются детерминированно по корню и точным байтам имени папки.
Текстовый список предназначен для просмотра. Для имён, которые нельзя надёжно
представить текстом, авторитетным является NUL-файл с исходными байтами. Оба
списка содержат только `SAFE_TO_DELETE`, но сами по себе ничего не выполняют.

#### Основные поля CSV

Идентификация и решение:

- `source_root`, `folder_name`, `absolute_path`;
- `decision` — `SAFE_TO_DELETE` или `BLOCKED`;
- `blocking_reasons` — отсортированный список причин блокировки;
- `classification_counts`, `scan_issue_types` — детализация файловых статусов и
  ошибок сканирования.

Точные итоги по физической папке:

- `storage_file_count`;
- `storage_total_size_bytes` — сумма логических `stat.st_size` всех
  отсканированных обычных файлов;
- `storage_total_size_human` — та же сумма в двоичных единицах.

Итоги LTO только для полных относительных путей, существующих в физической папке:

- `lto_matched_path_count`;
- `lto_known_size_file_count`, `lto_unknown_size_file_count`;
- `lto_conflicting_size_path_count`;
- `lto_additional_identical_tape_copy_count`;
- `lto_total_size_min_bytes`, `lto_total_size_max_bytes`;
- `lto_total_size_midpoint_bytes` и соответствующие поля `*_human`.

Полный итог соответствующей верхней папки во всём LTO-манифесте, включая пути,
которых нет на СХД:

- `lto_folder_manifest_file_count`;
- `lto_folder_manifest_known_size_count`;
- `lto_folder_manifest_unknown_size_count`;
- `lto_folder_manifest_conflicting_size_path_count`;
- `lto_folder_manifest_additional_identical_tape_copy_count`;
- `lto_folder_manifest_total_min_bytes`,
  `lto_folder_manifest_total_max_bytes` и поля `*_human`.

Поля разности имеют однозначное направление «СХД минус LTO»:

- `storage_minus_lto_min_bytes`, `storage_minus_lto_max_bytes`,
  `storage_minus_lto_midpoint_bytes`;
- `storage_minus_lto_manifest_min_bytes`,
  `storage_minus_lto_manifest_max_bytes`;
- соответствующие поля `*_human` сохраняют знак, например `+12.34 MiB`,
  `-8.17 GiB` или `0 B`.

Для обратной совместимости также сохраняются прежние поля `status`, `top_folder`,
`absolute_folder`, `file_count`, `verified_file_count`, `total_size_bytes`,
`lto_copy_count` и `lto_tapes`.

### Диагностические размеры верхних папок

Оба отчёта решений и общий `folder_size_comparison.csv` содержат точную сумму
логических `stat.st_size` всех отсканированных обычных файлов физической папки.
Для LTO выводятся два независимых диапазона:

- сумма записей LTO, чьи полные нормализованные пути присутствуют в этой
  физической папке;
- сумма всех путей манифеста с тем же нормализованным именем верхней папки,
  включая отсутствующие на СХД пути.

Минимумы и максимумы складываются из сохранённых интервалов округления YoYotta.
Середина диапазона предназначена только для визуального сравнения и не является
точным размером LTO. Разности всегда вычисляются как «точный размер СХД минус
соответствующее значение LTO» и в человекочитаемых полях сохраняют знак.
Счётчики путей и LTO-суммы используют уникальный нормализованный полный путь;
физические файлы и точная сумма СХД по-прежнему считаются отдельно для каждого
корня и по точным байтам имени верхней папки.

Повтор одного пути с одинаковым известным интервалом на нескольких кассетах
входит в логическую сумму один раз; дополнительные копии считаются по уникальным
именам кассет отдельно. Повтор строки той же кассеты не увеличивает этот счётчик.
Если у пути есть один известный интервал и записи с неизвестным размером,
известный интервал входит в диагностическую сумму один раз, но путь также
считается имеющим неизвестный размер и результат диапазона становится
`UNKNOWN_LTO_SIZES`. Если все размеры пути неизвестны, байты для него не
добавляются. Несколько разных известных интервалов считаются конфликтом: путь
учитывается в счётчике конфликтов, но его байты не выбираются произвольно и не
входят в сумму. Поэтому конфликт также даёт `UNKNOWN_LTO_SIZES`.

Значения результата диапазона:

- `WITHIN_INTERVAL` — точная сумма СХД входит в полный известный диапазон;
- `OUTSIDE_INTERVAL` — не входит;
- `UNKNOWN_LTO_SIZES` — диапазон неполон из-за неизвестного размера или
  конфликтующих интервалов;
- `NO_MATCHED_LTO_PATHS` — ни один путь физической папки не найден на LTO;
- `NO_LTO_FOLDER` — в манифесте нет соответствующей верхней папки.

Результат для совпавших полных путей записывается в
`folder_size_interval_result`, а результат для всей верхней папки LTO — в
`manifest_folder_size_interval_result`. Поле
`storage_size_within_lto_folder_interval` содержит `YES` или `NO` только при
полностью известном диапазоне; для неизвестного, конфликтующего или отсутствующего
диапазона оно остаётся пустым, а причина видна в `folder_size_interval_result`.

Эти суммы являются только диагностикой. Равенство сумм папки никогда не заменяет
пофайловую проверку и не меняет правила `SAFE_TO_DELETE`. Схема SQLite для этой
функции не изменяется: все значения вычисляются из существующих строк в режиме
только для чтения.

### Упрощённая операторская сверка папок

`simple_folder_check.csv` использует полный итог LTO-манифеста для того же
нормализованного имени верхней папки, а не только пути, найденные на СХД. Первые
шесть колонок имеют стабильный порядок:

1. `folder_name`;
2. `storage_size`;
3. `lto_size`;
4. `storage_file_count`;
5. `lto_file_count`;
6. `result`.

Далее записываются `source_root`, полный путь, точные размеры в байтах, границы и
середина LTO-интервала, разность, процент расхождения, раздельные результаты
размера/числа файлов, причина и активный режим PDF-единиц. Диагностические
счётчики `known_size_match_count`, `unknown_size_path_match_count`,
`storage_only_path_count`, `lto_only_path_count`, `size_mismatch_count`,
`conflicting_lto_path_count`, `ambiguous_path_count`, `zero_size_file_count`,
`scan_issue_count` и `invalid_encoding_count` позволяют проверить основание
решения без разбора текстового поля `reason`. `aggregate_size_result` содержит
`WITHIN_TOLERANCE`, `OUTSIDE_TOLERANCE` или `UNKNOWN`. `storage_size` и
`lto_size` показываются в общих двоичных единицах KiB/MiB/GiB/TiB уже после
перевода PDF-значений в байты. Если в папке есть и известные, и неизвестные
индивидуальные размеры, `lto_size` показывает сумму известных интервалов. При
полностью неизвестном или конфликтующем LTO-интервале значение равно `UNKNOWN`.

Поле `result` имеет четыре значения.

`YES` означает, что каждый файл СХД имеет точное совпадение полного
нормализованного пути и известного размера LTO. Дополнительно должны совпадать
множества путей и число файлов, агрегатный размер должен пройти настроенный
допуск, а неизвестные размеры, конфликты, неоднозначности, нулевые файлы,
ошибки сканирования и недопустимая кодировка отсутствовать.

`YES_WITH_UNKNOWN_SIZE` означает сигнал для ручной проверки. Он выставляется
только когда единственная причина, не позволяющая получить `YES`, — отсутствие
индивидуального размера у одной или нескольких точных LTO-записей. При этом:

- число файлов СХД равно числу уникальных путей полной LTO-папки;
- множества точных нормализованных относительных путей полностью совпадают;
- все LTO-записи с известным размером имеют пофайловый `MATCH`;
- присутствует хотя бы один `MATCH_PATH_ONLY_SIZE_UNKNOWN`;
- суммарный размер СХД проходит настроенный агрегатный допуск относительно
  суммы известных LTO-интервалов;
- нет `SIZE_MISMATCH`, отсутствующих или лишних путей, возможных переносов,
  неоднозначностей, конфликтующих LTO-записей, проблемных дублей СХД, нулевых
  файлов, ошибок сканирования и недопустимой кодировки.

Например, для развёрнутой последовательности First/Last PDF может подтверждать
все 190 точных путей, но не содержать индивидуальный размер одного
промежуточного кадра. Если остальные 189 файлов имеют `MATCH`, множества путей
и число файлов равны, а папочный размер проходит допуск, результат будет
`YES_WITH_UNKNOWN_SIZE`. Это не разрешение на удаление.

`YES_WITH_FILE_WARNINGS` означает, что точные множества путей и число файлов
совпадают, папочный размер проходит тот же агрегатный допуск, но один или
несколько известных индивидуальных размеров получили `SIZE_MISMATCH`. Статус
разрешён только при отсутствии лишних/недостающих путей, конфликтов,
неоднозначностей, нулевых файлов, ошибок сканирования и недопустимой кодировки.
Если одновременно есть точные пути с неизвестным индивидуальным размером,
результат также остаётся `YES_WITH_FILE_WARNINGS`, а `reason` содержит обе
диагностические причины. Это операторское предупреждение, а не строгое
подтверждение.

`NO` означает реальное расхождение, неоднозначность, неполное сканирование либо
другое неподдерживаемое или небезопасное условие. Совпадения только числа файлов
и общей суммы недостаточно: точное покрытие путей обязательно.

Допуск задаётся двумя независимыми условиями, объединёнными через OR:

- `--simple-size-tolerance-percent` — расширяет обе границы LTO-интервала на
  указанный процент от точного размера СХД; значение по умолчанию `0.1`%;
- `--simple-size-tolerance-bytes` — допускает расстояние до ближайшей исходной
  границы не более указанного числа байт; по умолчанию `10485760` (10 MiB).

Сравнение выполняется по целым байтам, а не по отформатированным строкам.
`size_difference_bytes` равно «размер СХД минус середина LTO-интервала»;
`size_difference_percent` — абсолютная разность относительно размера СХД в
процентах с четырьмя знаками после запятой.

Поле `reason` содержит `OK`, специальную причину
`INDIVIDUAL_LTO_SIZE_UNKNOWN_AGGREGATE_MATCH` для принятого операторского
сигнала, `INDIVIDUAL_SIZE_MISMATCH_AGGREGATE_MATCH` для пофайловых
предупреждений либо причины отказа в фиксированном порядке. При сочетании
неизвестного размера и `SIZE_MISMATCH` сначала записывается причина mismatch,
затем причина неизвестного размера:

1. `NO_LTO_FOLDER`;
2. `UNKNOWN_LTO_SIZE`;
3. `CONFLICTING_LTO_ENTRIES`;
4. `STORAGE_ONLY_PATH`;
5. `LTO_ONLY_PATH`;
6. `SIZE_MISMATCH`;
7. `AMBIGUOUS_PATH`;
8. `FILE_COUNT_MISMATCH`;
9. `SIZE_OUTSIDE_TOLERANCE`;
10. `ZERO_SIZE_FILE`;
11. `SCAN_INCOMPLETE`;
12. `INVALID_FILESYSTEM_ENCODING`.

Та же шестиколоночная таблица печатается в терминал. Длинные имена сокращаются
только при выводе на экран, но не в CSV. Если одинаковое имя папки присутствует
под несколькими корнями, к экранному имени добавляется короткий идентификатор
корня. После таблицы отдельно выводятся число папок и суммарный размер для
`YES`, `YES_WITH_UNKNOWN_SIZE`, `YES_WITH_FILE_WARNINGS` и `NO`, а также
активные настройки единиц и допусков. Для старой базы без `pdf_size_units` перед
таблицей печатается заметное предупреждение.

Важно: упрощённые статусы не изменяют строгое решение. Только папки с
`SAFE_TO_DELETE` попадают в `deletable_folders.csv`, `deletable_folders.txt` и
`deletable_folders.nul`. Папка с `YES_WITH_UNKNOWN_SIZE` остаётся в
`blocked_folders.csv` и требует ручной проверки. То же относится к
`YES_WITH_FILE_WARNINGS`: любой индивидуальный `SIZE_MISMATCH` блокирует строгое
решение. Агрегатный допуск не доказывает побайтовую идентичность и никогда не
смягчает строгие правила.

## Основные отчёты

- `summary.csv`, `summary.json` — общая статистика.
- `all_results.csv` — по одной итоговой строке на нормализованный путь.
- `matches.csv` — совпавшие пути и размеры.
- `size_mismatches.csv` — путь совпал, размер не попал в интервал округления YoYotta.
- `missing_on_lto.csv` — есть на СХД, отсутствует на кассетах; только эти записи попадают в автоматические copy lists.
- `missing_on_storage.csv` — есть в манифесте LTO, отсутствует на СХД.
- `possible_moved.csv` — тот же файл, вероятно, находится в другом подкаталоге той же верхней папки.
- `ambiguous.csv` — неоднозначные случаи, которые нельзя использовать для автоматического решения.
- `zero_size.csv` — нулевые файлы на любой стороне.
- `lto_duplicate_paths.csv` — один относительный путь присутствует в нескольких LTO-записях/на нескольких кассетах.
- `duplicate_manifest_locations.csv` — одна и та же кассета и тот же путь повторились в нескольких PDF или несколько раз в одном манифесте.
- `storage_duplicate_paths.csv` — один относительный путь найден под несколькими Linux-корнями.
- `parse_issues.csv` — особенности и ошибки разбора PDF.
- `scan_issues.csv` — ошибки чтения каталогов или `stat`, а также имена с байтами вне UTF-8.
- `report_stats.csv` — число файлов из заголовка каждого PDF и число извлечённых записей.
- `lto_manifest.csv`, `storage_manifest.csv` — полные промежуточные каталоги.

## Списки для последующего копирования

- `missing_on_lto_absolute_paths.txt` — абсолютные пути, по одному в строке.
- `missing_on_lto_absolute_paths.nul` — те же пути с NUL-разделителем; безопаснее для Bash.
- `missing_on_lto_shell_quoted.txt` — абсолютные пути, экранированные для оболочки.
- `copy_lists_by_root/` — относительные текстовые и NUL-списки отдельно для каждого массива.

Пример безопасного чтения NUL-списка без выполнения копирования:

```bash
while IFS= read -r -d '' file; do
    printf '%s\n' "$file"
done < ~/lto-audit/KANSK/missing_on_lto_absolute_paths.nul
```

Для `rsync` удобнее использовать файл `copy_lists_by_root/root_XX_relative_paths.nul` вместе с корнем, указанным в `copy_lists_by_root/roots.csv`:

```bash
rsync -a --dry-run --from0 \
  --files-from=copy_lists_by_root/root_01_relative_paths.nul \
  /mnt/AUDIT_RO/VIDEO6_SOURCE/ /path/to/destination/
```

Сначала обязательно использовать `--dry-run`. Сам скрипт копирование не запускает.

- любые записи из `zero_size.csv`
- любые записи из `parse_issues.csv` и `scan_issues.csv`


## Имена файлов вне UTF-8

На Unix имя файла является последовательностью байтов и не обязано быть корректным UTF-8. Такие имена иногда остаются после старых Mac/Windows-кодировок. Версия 1.0.1 и новее:

- продолжает сканирование вместо ошибки `surrogates not allowed`;
- показывает проблемный байт в CSV как `\x92`, `\xA0` и т. п.;
- сохраняет исходные байты пути в SQLite BLOB;
- записывает событие `non_utf8_filesystem_name` в `scan_issues.csv`;
- исключает запись из автоматического сравнения и copy lists, потому что PDF содержит Unicode-текст и безопасно установить соответствие без ручной проверки нельзя.

Число таких путей выводится как `non_utf8_paths` после сканирования и как `NON_UTF8_STORAGE_PATHS` в `summary.csv`.

## История запусков

SQLite-файл и CSV являются снимком одного запуска. Для сохранения истории используйте новый `--out-dir` для каждой проверки, например:

```text
~/lto-audit/KANSK/2026-07-22_before_copy/
~/lto-audit/KANSK/2026-07-23_after_copy/
```
